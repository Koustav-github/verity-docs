Quickstart

From a trained model to a served one.

Verity runs on your own infrastructure — your S3 bucket, your database, your LLM key. Nothing is hosted for you, and no credentials ship with the repo.

1. What you need

RequirementWhy
Python 3.12Server and SDK
DockerBuilds and runs one container per promoted version
An S3 bucketStores model artifacts and evaluation fixtures
A Supabase projectRelational store for every pipeline row
An OpenAI-compatible LLM keyHawkeye and Nat; defaults to Groq

2. Configure the server

Create server/.env:

S3_BUCKET=your-bucket
S3_REGION=us-east-1

SUPABASE_URL=https://your-project.supabase.co
SUPABASE_KEY=your-service-key
SUPABASE_DB_URL=postgresql://...

VERITY_LLM_API_KEY=your-key
# Optional — defaults to Groq
VERITY_LLM_BASE_URL=https://api.groq.com/openai/v1

AWS credentials are not read from this file. Boto3 resolves them through its standard chain — environment variables, ~/.aws/credentials, or an instance role.

3. Run it

# Server
cd server
uv sync --extra dev
uv run alembic upgrade head
uv run uvicorn main:app --port 8000

# Frontend (optional, in a second shell)
cd client
npm install
npm run dev
Note: uv sync without --extra dev prunes pytest from the venv, and uv run pytest then silently falls back to a different interpreter. Always pass the flag.

4. Install the SDK

pip install -e ./verity

5. Upload a model

Pass a fitted model and a holdout set. name is what groups versions — uploading again under the same name creates a new version of the same model. 

from verity import assemble

result = assemble(
    model,                       # any fitted sklearn / XGBoost / LightGBM estimator
    user_id="demo-user",
    name="titanic-survival-classifier",
    endpoint="http://127.0.0.1:8000",
    X_test=X_test,
    y_test=y_test,
    alert_email="ops@example.com",   # optional
)

print(result["status"])              # production | staging_failed | pending
print(result["model_version_id"])

Or from the command line:

verity --demo --user-id demo-user --name demo-classifier
First upload is slow. It includes a full Docker image build — around three minutes cold. Later versions on the same dependency set reuse the cached pip layer and take seconds.

6. Call the model

Once a version reaches production, call it through Verity's proxy. This address is stable across promotions and is what records telemetry. 

import requests

response = requests.post(
    "http://127.0.0.1:8000/users/demo-user/models/titanic-survival-classifier/predict",
    json={"instances": [
        {"Pclass": 3, "Sex": 0, "Age": 22, "Fare": 7.25, "Embarked": 2.0, "Relatives": 1}
    ]},
)
print(response.json())
# {"predictions": [...], "probabilities": [...], "prediction_id": "pred_..."}

If the model was fitted on a DataFrame, instances takes objects keyed by column name and the recorded column order wins. If it was fitted on a bare array, send lists of values instead.

7. Report outcomes (optional)

When ground truth arrives later, report it back. Once 30 labels accumulate, Falcon re-runs the exact metric set and thresholds frozen at promotion time and raises a quality alert if the model has drifted below them. 

requests.post(
    f"http://127.0.0.1:8000/predictions/{prediction_id}/outcomes",
    json={"outcomes": [{"index": 0, "actual": 1}]},
)

Serving on Fargate instead

VERITY_CONTAINER_RUNTIME=fargate
VERITY_FARGATE_ECR_URI=...
VERITY_FARGATE_EXECUTION_ROLE_ARN=...
VERITY_FARGATE_SECURITY_GROUP=...
VERITY_FARGATE_SUBNETS=subnet-a,subnet-b

Nothing else changes. Both runtimes sit behind the same interface, and the deployment row records whichever endpoint the task actually came up on.
