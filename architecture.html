Architecture

What happens between upload and serving.

One /ingest call runs the whole chain synchronously. Each stage writes its evidence before the next begins, so a failure leaves an explanation behind rather than a gap.

The pipeline

assemble(model, X_test=…, y_test=…)
      │  multipart: artifact + fixture + descriptor
      ▼
POST /ingest
      ├─ store artifact + fixture           → S3
      ├─ Hawkeye: identify + introspect     → manifest row
      ├─ Nat:     resolve → run → score     → eval_run row
      ├─ Fury:    gate → register → archive → model_version row
      ├─ Falcon:  configure monitoring      → monitoring_config row
      └─ deploy:  build → run → healthcheck → deployment row

Status, and what moves it

StatusMeans
pendingIdentified and stored, but no fixture was supplied so nothing was evaluated
staging_failedEvaluated and missed at least one threshold — failed_on names which
productionCleared every threshold and was promoted; this is the version the predict route resolves to
archivedWas in production until a newer version replaced it; keeps its own evidence

Evaluation is pluggable

Nat dispatches on the fixture's kind rather than knowing how to evaluate anything itself. Only labeled_holdout is registered today; images, RAG corpora, and RL rollouts each arrive as a new module plus a registry line, without touching the ingest path or the row shape.

Resource metrics sit outside that: the sandbox harness measures latency, throughput, memory, and CPU on every run regardless of mechanism, and stores them under a reserved resource. prefix in the same flat scores object. Thresholds gate on either kind through identical plumbing.

The sandbox

A model's predict() runs in a fresh subprocess started with a scrubbed environment — no database key, no blob store key, no LLM key. Unpickling is arbitrary code execution, and this process is the containment boundary for it. There is a test that sets a credential in the parent and asserts the child cannot read it.

Serving

Each promoted version becomes its own container image, built from the library versions the SDK captured on the training machine. A pickle is only reliably loadable against the versions that wrote it, so a single shared serving image was never an option — and the capture has to happen client-side, since introspecting on the server would faithfully describe the wrong machine.

The artifact is copied into the image, which means the serving container needs no credentials at all — the same principle the eval sandbox reached from the other direction.

Two runtimes, one interface

DockerRuntime and FargateRuntime both implement build / run / stop. run() returns the endpoint it actually came up on, so nothing above that layer assumes localhost.

Deploy is non-fatal

Deployment and monitoring both run after a version is already promoted. A build failure records its reason on a failed deployment row and returns deployment: null — it never retroactively fails a promotion that genuinely succeeded.

Monitoring

Falcon needs no LLM. When Fury promotes a version, the eval run that justified it already holds measured latency percentiles, throughput, memory, and quality scores, so the baseline is lifted from evidence rather than guessed.

Two checks run inline, triggered by the events that already move data — no scheduler, no poller. The systemic check compares a version's trailing 15 minutes against the 15 before it. The quality check re-runs Nat's own scoring against accumulated labels, using the exact thresholds frozen at promotion.

Deliberately not compared: live traffic is never measured against the sandbox eval numbers. Those are cold, single-client figures that always look better than production, and comparing against them would manufacture false alarms.

Limits this version accepts

No authentication on any route. Every endpoint is open, including /ingest, which accepts arbitrary pickles. Run this locally or behind your own network boundary.
  • Resource metrics are feasibility numbers. Single-process, single-client, cold sandbox — not production p99.
  • Single replica. No autoscaling, no idle shutdown, no load balancer. A local deployment lives and dies with the machine running Verity.
  • Promotion is not comparative. A version that clears its own thresholds replaces the incumbent even if the incumbent scored better. Both keep their evidence, so it is visible — but it is not prevented.
  • Tabular and classical ML only — scikit-learn, XGBoost, LightGBM.
  • Not built yet: input drift detection, the agent audit trail, autonomous retraining.
