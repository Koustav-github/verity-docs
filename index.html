Overview

One call, and the model is evaluated, served, and watched.

Verity is an MLOps pipeline built around four agents. You hand it a trained model and a holdout set; it identifies the model, decides what to measure, gates promotion on the result, builds and runs a container for it, and monitors the traffic that follows. 

from verity import assemble

result = assemble(
    model,
    user_id="demo-user",
    name="titanic-survival-classifier",
    X_test=X_test,
    y_test=y_test,
)

That single call runs the whole loop. A model that clears its thresholds is promoted to production and served; one that misses stops at staging_failed with the specific thresholds it failed recorded against it.

The four agents

Hawkeye Identifies the model — framework, class, task type — and introspects its input surface so the served API can be generated rather than guessed.
Nat Resolves a task-appropriate metric set and thresholds, runs the model in a credential-free sandbox, scores it, and returns a verdict.
Fury Gates promotion on that verdict, registers the version under its model name, and archives the version it replaces.
Falcon Configures monitoring from the eval evidence, then detects anomalies in live traffic and raises alerts.

Agents configure, pipelines execute

This is the principle the whole design follows. An LLM picks the configuration once — which metrics suit this task, what thresholds are reasonable for this dataset. Everything after that is deterministic: the scoring is plain scikit-learn, the threshold comparison is plain code, and the numbers are frozen onto an append-only row as they were applied.

A later change to how thresholds are chosen can never retroactively alter what a past gate decided.

Gating on more than accuracy

Nat measures latency percentiles, throughput, peak memory, and CPU time alongside quality metrics, and a threshold on either kind gates identically. A model that is accurate but too slow to serve does not pass — which, for a pipeline whose job is to decide whether something is worth serving, is arguably the more load-bearing half.

Stated plainly: those resource numbers come from a single-process, single-client, cold sandbox. They answer “can this be served at all”, not “how does it behave under production load”.

What ships in v1

  • The four-agent pipeline, fully automatic on every upload
  • One container image per promoted version, built from the captured training environment
  • Local Docker or AWS ECS Fargate serving, behind the same runtime interface
  • A stable predict route that survives promotions
  • A registry UI for browsing versions and their evidence
  • Verified end to end on scikit-learn, XGBoost, and LightGBM
