API

SDK and HTTP reference.

Python SDK

assemble()

Uploads a trained model for identification, evaluation, registration, and serving.

from verity import assemble

assemble(
    model,                    # a fitted estimator
    user_id: str,
    name: str,                # groups versions; same name = new version
    endpoint: str = "http://localhost:8000",
    X_test=None,
    y_test=None,
    fixture: tuple | None = None,
    alert_email: str | None = None,
    timeout: float = 600.0,
) -> dict
ArgumentNotes
nameThe only thing deciding whether an upload is a new model or a new version of an existing one
X_test / y_testThe shortcut for a labeled holdout. Omit both and the model is stored and identified but never evaluated — status stays pending
fixtureA (payload, descriptor) pair for fixture kinds with no keyword shortcut
alert_emailSet once, on first registration. A later version's upload never silently changes who gets notified
timeoutDefaults to 600s because a first deploy includes a cold Docker build

Returns the full record: model_version_id, status, manifest, eval_run, deployment, monitoring_config.

monitor()

For models you serve yourself. Wraps the model so predictions are reported back to Verity; .predict() behaves identically. 

from verity import monitor

wrapped = monitor(model, model_version_id="mv_...")
wrapped.predict(X)

Telemetry can never be why inference fails or slows: reporting happens on a background thread, drops on a full queue, and if the model raises, the caller gets that exact exception back — recorded, then re-raised unchanged.

HTTP routes

Predict

POST /users/{user_id}/models/{name}/predict

Resolves whichever version is currently in production and forwards to its container. Stable across promotions, and the only path that records telemetry. 

{"instances": [{"feature": 1.0, ...}]}   // named-feature models
{"instances": [[1.0, 2.0, ...]]}         // positional models

Returns predictions, probabilities, and a prediction_id.

StatusMeans
404No production version under that name — or promoted but not deployed. The two are distinguished in the message
422Instance shape mismatch; the message names the exact features expected
502The container did not answer

Registry

RouteReturns
GET /users/{user_id}/modelsEvery model for a user, with its production version id
GET /models/{model_id}/versionsThat model's versions, newest first
GET /model_versions/{id}Full evidence: manifest, eval run, deployment, monitoring config
GET /model_versions/{id}/download-urlsPresigned S3 links for artifact and fixture, 15-minute expiry

The list routes return an empty list for an unknown id rather than 404 — there is no user table to check existence against. The detail routes do 404, since those name one specific thing.

Observability

RouteReturns
GET /models/{version_id}/telemetryRequest count, error rate, latency percentiles, and recent calls
GET /models/{version_id}/alertsAlerts Falcon has raised for this version
POST /telemetryBatch ingest, used by verity.monitor()
POST /predictions/{id}/outcomesReport ground truth for a past prediction
Traces omit payloads on purpose. Inputs and predictions are recorded server-side, but the telemetry route projects only timing and status. Serving real production inputs through an unauthenticated endpoint is not something v1 does.

Ingest

POST /ingest    # multipart: model, sha256, user_id, name,
                #            fixture, fixture_descriptor, environment

Use the SDK rather than calling this directly — it handles serialization, hashing, and environment capture. A byte-identical re-upload under the same name is a true no-op and returns the existing record with deduplicated: true.
